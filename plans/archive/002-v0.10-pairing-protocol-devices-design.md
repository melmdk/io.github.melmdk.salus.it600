# Design: v0.10 — pairing that reuses the connection, protocol detection, new devices

**Status:** Implemented (v0.10.0, installed on homey-1 as f5ba5bb on 2026-10-27)
**Created:** 2026-10-26
**Base:** branch `fix/poll-robustness` (commit `4e6e153`) on top of v0.9.6

## Why

The app is the owner's local, cloud-free integration of their Salus IT600 heating: one **UGE600** gateway (firmware `021800260717`, AES-256-CBC), ten **SQ610RFNH** thermostats, two **it600WC** wiring centres ("Kældertrappe", "Depotrum"), one RE600 repeater and one offline SQ610 ("Multirum").

Moving the gateway to a new VLAN on 2026-10-26 exposed several problems:

- Every pairing asks for IP and EUID again, even though the app already has a working connection. This is repeated in five drivers.
- The settings page saves `host` and `euid` as two separate writes. The first reconnect runs with the new IP and the *old* EUID, and shows a misleading error.
- A decryption failure reaches the user as the raw Node error "bad decrypt", not "wrong EUID".
- The EUID placeholder in pairing (`001E5E0D32906128`) looks like a real EUID. It ended up saved as the EUID.
- The thermostat driver implements `onRepair`, but no repair views are declared, so Repair doesn't exist in the UI.
- One thermostat (Mikkel) was missing from the pairing list. The gateway reported it, but the list came from the last cached poll.
- The upstream library the app was ported from (`pyit600`, last release 0.5.1 in 2022) is dead. Its maintained successor, [`salus-it600-client`](https://github.com/Jordi-14/salus-it600-client) (0.7.0, 2026-10-26, MIT/Apache-2.0), adds features that matter for this setup.

## Goals

1. **Pairing and repair reuse the existing connection.** If the app already has a connected gateway, pairing goes straight to the device list. The credentials screen appears only on first setup, or when the saved gateway can't be reached. It is pre-filled with the saved IP.
2. **One gateway-credentials flow shared by all drivers** for pairing, repair and the settings page, instead of five copies.
3. **Errors a user can act on:**
   - wrong EUID → "Wrong EUID: check the 16 characters on the gateway label"
   - unreachable → "No gateway answering at <ip>"
   - unsupported protocol → "Gateway firmware uses an encryption this app doesn't support"
4. **The settings page saves IP and EUID as one change**, so the app reconnects once, with the new pair.
5. **Repair works for every driver.** It re-runs the shared credentials flow and reconnects the app-level gateway, which all devices share.
6. **The pairing list is fresh.** It runs a new poll before listing and merges with the last-seen cache, so a device that drops out of a single poll is still offered.
7. **Protocol auto-detection.** Try AES-256-CBC (today's scheme), then AES-128-CBC, then AES-256-CCM (newer UG800 firmware), in that order, as `salus-it600-client` does. Remember the detected protocol in app settings so restarts don't probe. Probe again if the remembered protocol stops working.
8. **Combined detail requests: opt-in, verified.**
   - **One request per device type stays the default.** The owner doesn't remember why v0.9.6 reverted combined requests ("thermostat updates didn't reflect in Homey"), so stale data can't be ruled out. The reference fallback triggers (rejected, devices left out, three drops) wouldn't catch stale data.
   - Combined requests are implemented with the reference fallback, but only switched on after a **live write-then-read check** passes on the owner's gateway: write a setpoint, then confirm a combined poll returns the new value within one poll cycle.
   - If the check fails, or devices are routinely left out (for example, the offline "Multirum"), combined requests stay off. The plan records the outcome.
9. **New features ported from `salus-it600-client`:**
   - **SQ610 "Away" preset** (`HoldType` 6, written via `SetHoldType`), added to `salus_preset_mode`.
   - **Signal diagnostics.** RSSI (`LastMessageRSSI_d`) and LQI (`LastMessageLQI_d`) on thermostats and wiring centres. Keep the last value when a poll omits them.
   - **Wiring centre (it600WC) as a new device type**, diagnostic only:
     - connectivity, reflected in device availability plus a connected indicator
     - a "problem" alarm built from the `sIT600WC` fault registers and `ErrorCodeWC_d` (hex string; `"0000"` means no fault)
     - RSSI/LQI
   - **Thermostat problem alarm** from the `ErrorNN` flags in `sIT600TH`, using the vendor descriptions from the reference library's error table.
10. **Tests.**
    - Parsers and protocols get unit tests.
    - Parsers are tested against **fixtures captured from the owner's real gateway**, sanitised as described under Constraints.
    - CBC is tested against the real gateway's behaviour (known request/response pairs).
    - CCM is tested against vectors generated with the reference algorithm, because no UG800 is available.

## Non-goals

- The Salus cloud API, or any cloud dependency
- Editing schedules
- Buttons (SB600/CSB600); the reference library doesn't support them either
- SQ610 advanced-settings decoding, floor probe, TRV3RF features
- Publishing to the Homey App Store. The owner decides that after review.
- Toolchain upgrades: TypeScript 7, ESLint 8+, replacing the `@types/homey` alias

## Anti-goals (failure even if it "works")

- **Breaking existing devices.** Already-paired devices must keep their IDs, capabilities and flows. New capabilities are added in `onInit` with `addCapability` when missing. Nothing is removed.
- **An app that stops polling or never reconnects.** Keep the behaviour of commit `4e6e153`: polling always runs and reconnects on its own.
- **Sending the EUID or Wi-Fi fields to the log,** or committing them in fixtures.
- **Probing protocols on every poll** or on every app restart once a protocol is known.
- **More than one request in flight to the gateway.** It handles few concurrent connections; keep the existing mutex.

## Constraints

- Homey SDK 3, `compatibility >=12.4.0`, TypeScript 5.9, the existing `@tsconfig/node16` base.
- The app is **GPL-3.0**. Code ported from `salus-it600-client` (MIT/Apache-2.0) is allowed, with attribution in a `NOTICE` file and the source named in file headers.
- **Fixture sanitisation:** before committing captured gateway responses, remove or replace these `sGateway` fields: `NetworkSSID`, `NetworkPassword`, `LocalModeAccessCode`, MAC/IP fields. No EUID anywhere in the repo, apart from the git-ignored `test-config.json`.
- **Test hardware:** only the owner's UGE600 (CBC) is available. CCM must be correct by construction plus test vectors.
- **Project conventions** (CLAUDE.md): Conventional Commits with the existing scopes, plus `pairing`, `wiring-centre` and `api` as needed. Plans live in `plans/`. Version bump in `.homeycompose/app.json`, `package.json` and `CHANGELOG.md`.

## Decisions made in the conversation

- The owner chose all four areas: skip credentials when connected, fix the paper cuts, port new devices and sensors, future-proof the protocol.
- The uncommitted work was committed as its own commit (`4e6e153`, `setMaxListeners(50)` restored). The new work builds on it.
- Keep the app local-only. Don't switch to the community cloud app.
- **The cause of the February combined-request revert is unknown.** Per-type stays the default, and combined requests only switch on after the live check in goal 8.
- **The owner approved this live access** (2026-10-26):
  - read-only polls and fixture capture from the dev machine
  - deliberately wrong EUID and AES-128-CBC/CCM probes against the real UGE600, to confirm the error mapping
  - writes to **one thermostat: "Gæsteværelse"** (setpoint change and Away). Name it in the plan before each write session, and restore the original preset and setpoint afterwards.
  - running `salus-it600-client` 0.7.0 in a throwaway Python venv, **only to generate CCM test vectors**, with no gateway or network access from it. Vectors from the reference code are the proof that the TypeScript CCM is correct, including 12-character EUID handling and the nonce layout.

## My calls (the builder may revisit; check them while reading)

- **Version 0.10.0**, a minor bump because there are new features and nothing breaks. Work goes on branch `feat/v0.10` from `fix/poll-robustness`.
- **Wiring centres become their own driver** (`wiring-centre`), not capabilities on another device. They have no zone of their own in the UI otherwise.
- **RSSI/LQI become capabilities on existing devices** (custom `salus_rssi` in dBm and `salus_lqi`, read-only, no insights by default), not separate devices.
- **The thermostat problem alarm** uses `alarm_generic`, plus a read-only text capability listing the active fault descriptions. A flow trigger fires when a fault appears.
- **Credentials state lives at app level** (`gateway` setting: host, euid, protocol). Drivers ask the app for the connection; they never create gateways themselves.
- **Test runner: Node's built-in `node:test`** on the compiled output. No new runtime dependencies.
- **"Temporary Hold" keeps its current name.** The reference library calls it "Schedule Override", but renaming would change existing users' values.
- **SQ610 preset reporting doesn't change, apart from adding Away.** Today HoldType 1 on an SQ610 reads as "Follow Schedule", and choosing "Temporary Hold" writes Follow Schedule (`lib/salus-api.ts`, around lines 801–802). Adopting the reference mapping would change what existing flows see, which the anti-goals rule out. This is documented as a known limitation.
- **CBC test data:**
  - Committed fixtures are sanitised plaintext, **re-encrypted under a dummy EUID**, keeping the real framing quirks: the non-block-aligned trailer and the 33-byte reject frame.
  - Raw captures under the real EUID live only in a git-ignored `test/local/` folder. Tests that need them skip when the folder is missing.
